|---|----------|--------|-----------|
| 1 | Phase 순서 | Phase 0 (Apify 검증) 선행 | 스키마가 실제 데이터 형태에 의존 |

## DB Schema (draft — Phase 0에서 Apify 데이터 형태 확인 후 확정)

```sql
-- 스크래핑 작업
CREATE TABLE scrape_jobs (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  username TEXT NOT NULL,
  apify_run_id TEXT,
  status TEXT NOT NULL DEFAULT 'pending',  -- pending, scraping, ready, failed
  error_message TEXT,
  post_count INTEGER,
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now()
);

-- 분석 대상 계정
CREATE TABLE accounts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  username TEXT UNIQUE NOT NULL,
  display_name TEXT,
  profile_pic_url TEXT,
  follower_count INTEGER,
  last_scraped_at TIMESTAMPTZ,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- 게시물
CREATE TABLE posts (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  account_id UUID REFERENCES accounts(id) ON DELETE CASCADE,
  apify_id TEXT UNIQUE NOT NULL,        -- Apify가 제공하는 고유 ID
  text_content TEXT,
  media_type TEXT,                       -- text, image, carousel, video
  like_count INTEGER DEFAULT 0,
  repost_count INTEGER DEFAULT 0,
  reply_count INTEGER DEFAULT 0,
  total_engagement INTEGER GENERATED ALWAYS AS (like_count + repost_count + reply_count) STORED,
  outlier_score REAL,                    -- 배수 (예: 5.3)
  posted_at TIMESTAMPTZ,
  scraped_at TIMESTAMPTZ DEFAULT now(),
  raw_data JSONB                         -- Apify 원본 데이터 보존
);

-- LLM 분석 결과
CREATE TABLE analyses (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  post_id UUID REFERENCES posts(id) ON DELETE CASCADE UNIQUE,
  hook_analysis TEXT,
  emotion_analysis TEXT,
  structure_analysis TEXT,
  cta_analysis TEXT,
  conversation_analysis TEXT,
  sharing_analysis TEXT,
  hook_type TEXT,                         -- curiosity, number, shock, empathy, prediction, experience
  metadata_analysis JSONB,               -- 미디어, 길이, 타이밍, 타래 분석
  full_response TEXT,                    -- LLM 전체 응답 보존
  created_at TIMESTAMPTZ DEFAULT now()
);

-- 컬렉션 (단일 컬렉션)
CREATE TABLE collection_items (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  post_id UUID REFERENCES posts(id) ON DELETE CASCADE UNIQUE,
  created_at TIMESTAMPTZ DEFAULT now()
);

-- 패턴 분석 결과 캐시
CREATE TABLE pattern_analyses (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  item_count INTEGER NOT NULL,           -- 분석 시점의 컬렉션 아이템 수
  patterns JSONB NOT NULL,               -- 패턴 카드 배열
  full_response TEXT,
  created_at TIMESTAMPTZ DEFAULT now()
);
```

## 아웃라이어 점수 계산 (상세)

```
입력: 계정의 전체 게시물 (시간순 정렬)
기준: 최신 10개 게시물의 평균 total_engagement

계산:
  avg = sum(latest_10.total_engagement) / 10
  for each post:
    outlier_score = post.total_engagement / avg

엣지 케이스:
  - 게시물 < 11개: avg를 전체 게시물 평균으로 대체. UI에 "게시물이 적어 전체 평균 기준" 표시.
  - avg == 0: outlier_score = 0. 모든 게시물이 0 engagement.
  - 최신 10개 중 삭제된 게시물: Apify가 반환하는 게시물만 사용.
  - 리포스트 전용 게시물: text_content 없으면 분석 불가. 아웃라이어 리스트에는 포함.
```

## 패턴 분석 추출 스키마

```typescript
// lib/prompts/pattern.ts에서 LLM에 요청하는 출력 구조
interface PatternCard {
  name: string;              // 패턴명 (예: "Curiosity Gap Hook")
  description: string;       // 패턴 설명 (1~2문장)
  evidence: {
    account: string;         // @username
    postSnippet: string;     // 게시물 첫 50자
    outlierScore: number;    // 배수
  }[];
  avgOutlierScore: number;   // 증거 게시물들의 평균 배수
  frequency: number;         // 발견 횟수
  actionGuide: string;       // "이 패턴을 내 글에 적용하려면..." (2~3문장)
}

// LLM 프롬프트에서 요구:
// - 최소 2개 이상의 증거가 있는 패턴만 포함 (minimum evidence threshold)
// - 같은 계정의 같은 표현은 1개로 카운트 (dedupe)
// - 패턴 간 중복 시 더 구체적인 패턴 우선 (conflict resolution)
// - JSON 형식으로 출력 강제 (structured output)
```

## Phase 분할

### Phase 0: Apify Actor 검증 (~15min CC)

```
범위:
  - Apify Threads Actor 리서치 + 선정
  - 실제 API 호출로 데이터 형태 확인
  - Zod 스키마 작성 (Apify 응답 + webhook payload)
  - DB 스키마 확정 (실제 데이터 기반)

의존: 없음
산출: Zod 스키마, 확정된 DB 스키마, 선정된 Actor ID
예상 LOC: ~150 (Zod 스키마 + 타입)
```

### Phase 1: Data Pipeline + UI 기본 (~30min CC)

```
범위:
  - Next.js 프로젝트 초기화 (create-next-app)
  - Supabase 프로젝트 생성 + 마이그레이션
  - 비밀번호 미들웨어 + 로그인 페이지
  - Server Action: startScraping (Apify run 시작 + job DB 저장)
  - API Route: /api/webhooks/apify (결과 수신 + 아웃라이어 계산 + DB 저장)
  - Supabase Realtime 구독 (scrape_jobs status 변경 감지)
  - 홈 페이지 (계정 입력만 — 순수 입력 터미널, 이력 없음)
  - 결과 페이지 (아웃라이어 리스트 + 슬라이더 2x~10x)
  - Unit 테스트: 아웃라이어 계산, Zod 스키마, 엣지 케이스

의존: Phase 0 완료
산출: 스크래핑 → 결과 표시 동작하는 앱
예상 LOC: ~800
```

### Phase 2: AI Analysis (~20min CC)

```
예상 LOC: ~500
```


## Worktree Parallelization

Phase 간 의존성이 순차적이므로 병렬 워크트리는 불필요:

```
Phase 0 → Phase 1 → Phase 2 → Phase 3 → Phase 4
(순차)     (순차)     (순차)     (순차)     (순차)
```

Phase 1 내부에서는 프론트엔드(UI)와 백엔드(API/webhook)를 병렬로 작업할 수 있지만,
단일 CC 세션에서 순차 실행이 더 효율적이다 (컨텍스트 공유).
